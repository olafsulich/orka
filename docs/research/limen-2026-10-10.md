## What changed in Limen since 38b2dc9

The context *architecture* was already landed at the base. `hook/communication.ts` at `38b2dc9` already put stable guidance on the system prompt, kept a short per-turn cue, and omitted the shop manual, vision body, and board digest from jobs. `hook/wake.ts` already clipped the final message to 15 lines and 1200 characters and commits to 10. `src/wrapper.ts` already had a 90-minute timeout and a 900 tool-start cap. The month since then did not add a compactor, a summary tree, or a forget command.

What did change, and matters for context:

- **Cues moved out of code.** `hook/communication.ts` dropped the hardcoded `REPLY_RULES` / `SPECS_REMINDER` strings. `templates/communication.md` now has `## Cue: Shared|Human|Agent|Wake|Failure|Specs|Search`. The hook copies the section body (not the heading) into the hidden per-turn note. A project register with no cue section adds nothing; there is no package fallback for a missing cue (`registerCue`).
- **Closing overview (F075, `dd85e7c`).** The Human cue and the register say a reply that hands control back with work in flight ends with a short overview: finished, running and which job, waiting on the owner. A job id is not the subject of a sentence. This is speech, not a smaller prompt.
- **Private planning and a ticket pointer.** Jobs follow the planning source recorded at spawn (`planning-source` on the job). Private mode adds `privatePlanningGuidance` to the system prompt and prefixes vision/board paths with the canonical root. The job cue still names `Ticket:` from `task.md` rather than inlining the ticket.
- **Jevgrep.** If `jg --help` mentions Jevgrep, the Search cue is appended to the system prompt once per `PATH`. Not a memory system.
- **Wake text extracted, bounds unchanged.** `handoffExcerpt` moved to `src/job/wake-text.ts`. Same clip. New sentences: a keeper hint on `done`, and `groupLeadWake` when a team coordinator finishes and the lead's group hook is down. `docs/jobs.md` (new) states both Pi session injection and `herdr agent prompt` carry the same bounded facts.
- **`docs/context.html` deleted** (`bb34219`, then `63e156e`). It was an interactive "how we guide agents" walkthrough, not the runtime. Claude-as-engine was dropped, then Pi and OMP became one profile (`src/runtime/engine.ts`). Workers still get the role file via `--append-system-prompt`.
- **Groups.** `src/job/group-events.ts` `acceptBatch` sends at most 8 events and 8000 characters. The rest stays in the cabinet and the message names that path. Not a coordinator memory.
- **Continue still copies the transcript.** `limen continue` seeds the child `.limen/jobs/<id>/session/` with a copy of the parent's newest `.jsonl` (`src/job/publication.ts`). That preserves context. It does not shrink it. F034's ticket explicitly left compaction out of scope.
- **Worker preamble grew a little.** `templates/worker.md` gained a ticket-contract block and a "new tests replace old tests" line. The reading budget ("ten reads without a changed file means make the probe edit") was already there.
- **Not context, do not import:** picture viewer, GitHub doorbell, spec keeper, `limen land`, `prune --retire`, speech removal, the F927 test reset, F936 Haiku scout notes (a study and a page, no scout role in `templates/`), F930/F931 OptChat explainer tickets (a lab page under `~/overment/lab/optchat-explainer/`, not plant `src/`).

`origin/main` does not implement OptChat. Typical Limen context is still: fill the thread, let Pi compact, keep rules on the system prompt, and put only a bounded excerpt in the wake.

## How Limen context management works

Limen does not compact transcripts itself. Pi (or OMP) compacts. Limen's job is to stop large, stable, or repeated text from entering the thread, and to leave the full record on disk.

There is no forget command, no archive of conversation turns, and no summary file the coordinator is required to reload after compaction. `limen prune --retire` deletes finished job *records* whose branch is landed or gone. That is disk housekeeping, not a resume summary. `docs/jobs.md` says spawn and sweep never retire records.

### 1. Two layers on every model call

`hook/communication.ts` (`limenCommunication`) listens to Pi `before_agent_start`.

`guidancePrompt` is appended to `event.systemPrompt` (stable, once per call, cacheable):

| Piece | Coordinator (`LIMEN_JOB` unset) | Job (`LIMEN_JOB=1`) |
|---|---|---|
| Shop manual `templates/agents.md` (only if the repo has no `AGENTS.md`) | yes, capped | omitted |
| Communication register, text above the first `## Cue:` | yes | yes |
| Vision `spec/vision.md` | yes, capped | omitted; path only in the cue |
| Styleguide `.agents/limen/styleguide.md` | yes, capped | yes, capped |
| Board digest: `## NOW` and `## NEXT` of `spec/build.md` only | yes | omitted; path only in the cue |
| Private-planning guidance | if the project setting is private | if the job record says private |
| Jevgrep Search cue | if `jg` is Jevgrep | same |

`boundText` keeps 1000 lines (`MAX_CONTEXT_LINES`) and appends `[path truncated to 1000 of N lines; read the file for remaining context.]`.

The per-turn note is a hidden message, `customType: limen-project-context`, `display: false`. It is rebuilt every turn, so it survives compaction even when file bodies do not. For a job it is: Shared cue, Agent cue, optional Failure cue (`{{failure}}` from the last assistant `stopReason`), Wake cue if the prompt starts with `Limen job `, `Ticket: <path>` from the first `Ticket:` in `.limen/jobs/<id>/task.md`, vision and board paths marked read-only, and a one-line "Last turn edited/wrote …" if the previous tool wrote a spec or code file or the bash looked like spawn/merge. It does **not** include the shop manual, the vision body, or the board body.

Coordinators also get drift text and, if `spec/build.md` is over 120 lines (`BOARD_ADVISORY_LINES`), one line telling them to fold older PROVEN entries. The digest itself is only NOW and NEXT, so PROVEN history is not re-sent every call.

After a write/edit, `tool_result` appends a reminder: spec paths get the Specs cue; other non-markdown paths get styleguide headings (at most 8, `MAX_REMINDER_HEADINGS`); vision-ish bash gets vision headings. The reminder is headings, not the file.

### 2. What a worker is actually prompted with

`src/commands/spawn.ts` `resolvePreamble` picks `.agents/limen/<role>.md` or `templates/<role>.md`. `src/runtime/engine.ts` `argvFor` passes it as `--append-system-prompt` and the task as `@<job>/task.md` (or `--continue <instruction>` for a continuation). Extensions loaded for a detached job are steering, communication, group-peer if a member, plus any recorded worker extensions. `--no-extensions` keeps ambient extensions off.

`templates/agents.md` tells the coordinator not to dump the ticket: a short instruction plus `Ticket: spec/features/.../ticket.md`. `docs/jobs.md` says the same. Over about two hundred words is a ticket problem. The worker preamble (`templates/worker.md`) says only commits, written files, and the final message survive the turn; reads are lost at exit. Before the first edit, read the ticket, the findings file if any, and the named file. Ten reads with no changed file means make the probe edit. If the slice is wider than the named seam, commit what is useful, write the question to a plain file, and finish.

Hosted jobs are told they have no timeout, no tool-call cap, and no process containment. Detached jobs do (`src/runtime/wrapper.ts`): default 90 minutes, 900 tool-start events (`LIMEN_MAX_TOOL_CALLS`), then the wrapper records `failed` and signals the process group. That bounds spend. It does not summarize.

The worker child environment strips `LIMEN_TASK_FILE`, `LIMEN_PREAMBLE`, model flags, and `HERDR_*`, and sets `LIMEN_JOB=1` plus `LIMEN_JOB_ID`. The communication hook uses those to choose the job column above. `LIMEN_CONTEXT_ROOT` is the canonical project root, not the worktree, so a job reads tickets and the board from the plant even when it edits a worktree.

Role files that exist and are omitted from ordinary workers: `templates/coordinator.md` (group team lead), `researcher.md`, `judge.md`, `quality.md`, `keeper.md`, `reviewer.md`, `group-member.md`. A worker does not receive the coordinator shop manual.

### 3. Completion wake: bounded excerpt, full text on disk

`src/job/wake-text.ts` `handoffExcerpt`:

- `stop-reason`, if present.
- `commits`: first 10 lines, or `Commits: none`, or omitted if the file is absent. Absence is information.
- `result`: first 15 lines, then sliced to 1200 characters. If clipped: `… (full text in the job record)`.
- count of files in `steer/inbox` that were never delivered.

`completionWake` leads with the label, the first sentence of `task.md` (capped at 240 characters), state, id, branch. It does not paste `task.md`, the log, or the session jsonl. Instructions differ for `done`, failed/stopped, produced-nothing (0 tool calls and no commits), and a busy-coordinator fallback ("do not spawn, stop, steer, or land").

Pi coordinators get that text injected by `hook/wake.ts`. OMP coordinators in Herdr get the same text via `herdr agent prompt` on the recorded pane (`docs/jobs.md`). A rejected injection during compaction releases the claim and retries; that retry existed before this range (F031) and is still the reason a wake must stay small.

`limen jobs` (piped) is the bounded health check: running rows, recent empty jobs (7 days, `RECENT_MS` in `src/commands/jobs.ts`), and a count of hidden terminal jobs. Human view shows running plus 6 terminal rows. Detail strings over 160 characters are cut. `templates/agents.md` says `limen jobs` is the check; `limen jobs <id>` is the detail. The coordinator is not told to cat the log into the turn.

On disk, a job directory (from `src/job/publication.ts` and later writes) holds `task.md`, `state`, `log`, `result`, `commits`, `stop-reason`, `tool-calls`, `session/*.jsonl`, `steer/inbox`, and routing files (`origin-pane`, `origin-session`). The wake points at that record. It does not inline it.

Hosted `finish` (`hook/hosted.ts`) writes the handoff argument to `result` and shuts down. `writeHostedResult` in `src/runtime/supervisor.ts` does not replace a tool-written result with a later "Done."

### 4. Continue, steer, groups

`limen continue <id> "instruction"` (`src/commands/continue.ts`) refuses a running job. It publishes a new job id with a `parent` file, copies the newest parent session jsonl, and runs the engine with `--continue` so the child resumes that transcript in the parent worktree. Reviewer continuation prints that it is not independent. This is the opposite of a fresh verifier.

`limen steer` writes an inbox file the steering hook delivers between tool calls. It does not append the steer to the coordinator transcript unless the coordinator typed it.

Group peer delivery is the only other clip: 8 events, 8000 characters, omitted count, path to the cabinet (`src/job/group-events.ts`). Unread events survive for a deliberate continuation. Limen does not respawn a finished member to deliver them.

### 5. What is not compacted

- Session jsonl grows until Pi compacts it. Continue copies that file as-is.
- The shop manual and styleguide are re-attached on the system prompt every call, capped at 1000 lines, not summarized.
- Worker logs are not clipped into the wake; they are simply not read by the wake builder.
- F936's "Haiku scout packet of 15 lines" is a study that reuses `handoffExcerpt`'s clip. It is not a shipped role.

## How orca context works today

Orca is a CLI. It does not load a hook into the agent. `README.md` says there is no coordinator conversation, no ticket board, and no package hooks in the target repo. Agents are started with `herdr agent start` (`startArgs` in `bin/orca.mjs`). Claude gets `--model <alias>` after `--`. Pi gets no extra arguments. Nothing passes `--append-system-prompt` or an extension. The only prompt injection is `herdr agent prompt`.

Searched and not found: a digest command, a token budget, a system-prompt layer, a per-turn cue, a clip on worker notes, a clip on `job.json`, compaction, or a resume of a worker session. `README.md` "v0 skips" lists resume, prune, and diff on purpose.

### What the orchestrator sees

`orchestratorPrompt` (`bin/orca.mjs`) is sent once, at `orca run`, via `promptWithRetry`. It includes the full `job.goal`, the worktree, the branch, port lines, and the operating rules: do not implement, shared worktree, do not push, do not close panes, how to start workers, verifier loop, `orca done` sends the finish wake, follow-up steer starts another round and `orca done` must be run again.

After that, the pane is a normal Pi or Claude session. Orca never re-sends the contract. If Pi or Claude compacts, the rules leave with the old turns. Nothing in orca notices.

During the job the orchestrator is told:

- Each worker writes `results/<name>.json` and `notes/<name>.txt`, then prompts with the one-line note. "Read those files."
- On verifier fail, read `results/verifier.json` and route each blocking failure **with its evidence** to a builder.
- Before `orca done`, read `<id>.json` again, write `summary.txt`, and set `job.summary`.

Those reads are unbounded. `job.json` stores every worker `task` and every steer message (`job.workers[]`, `job.steers[]`). A long goal plus a few verifier evidences makes the next turn large. `verify.log` is not named in the prompt, but nothing stops the agent from opening it.

`orca status` prints a short human view (summary, verifier line, stall). The orchestrator prompt does not tell it to use `orca status` as the context source except after a verifier round, to detect a stall.

### What a worker sees

`workerPrompt` is a fresh pane every `orca worker`. It includes the shared worktree, branch, port lines, browser-session name, the task string the orchestrator passed, and the instruction to write a JSON result, a one-line note, and `herdr agent prompt <orchestrator> "<note>"`. If the orchestrator is busy, the files are enough.

The task string is whatever the orchestrator typed. The orchestrator prompt tells it to paste verifier evidence verbatim into the next worker task. There is no 200-word cap and no "ten reads then edit" rule. The one-line note is a request, not a check. A worker can prompt the orchestrator with a log.

Workers share one worktree. They do not get a copy of the orchestrator prompt. That is already scoped, and it should stay that way. They also do not get a system-prompt preamble, a ticket pointer, or a tool-call cap. Orca does not wrap the agent process, so it cannot enforce a 900-call cap without a new supervisor. Do not add one.

### What the verifier sees

`verifierPrompt` says "You start with fresh context." It includes the full goal and the task the orchestrator passed (what was built and the acceptance criteria). It must not edit product code. Each round is a new pane (`verifier`, `verifier-2`, …). Starting the next round renames the previous `results/verifier.json` to `verifier.round-N.json` (`archiveVerifierResult`). That keeps the verdict file honest. It does not shrink anyone's prompt. The verifier prompt should stay as it is.

### What survives a follow-up steer

`cmdSteer` sends the human message as the entire `herdr agent prompt` body. It appends `{ at, message }` to `job.steers`. On a finished job whose orchestrator agent still exists, it sets `status` back to `running`, increments `job.round`, sets `followUp`, and starts the watcher again. It does not attach `summary.txt`, the last verifier verdict, the notes, or the contract.

What survives is whatever the pane still holds. `summary.txt` and `job.summary` are on disk (`summaryOf` reads the file, then `job.summary`). `orca status` prints the summary. The steer path does not. After compaction, a follow-up can lose the job id, the "do not implement" rule, and the requirement to call `orca done` again so the finish wake fires with `followUp: true`.

Panes stay open during the job. On `orca done` / `stop`, `releaseJob` closes worker panes, browser sessions, and worktree servers. The orchestrator pane and the workspace stay so Olaf can steer. `--keep` skips that cleanup and the later stale workspace sweep. A digest must not close panes and must not change `--keep`.

### What is written under `.orca/jobs`

- `<id>.json`: goal, workers (name, pane, task, result path, note path), steers, verifier state, summary field, round, keep, ports. Grows with the job. Not clipped.
- `<id>/results/<name>.json`: worker result, a few sentences by convention. Verifier JSON can hold long evidence.
- `<id>/notes/<name>.txt`: one line by convention. Not enforced.
- `<id>/summary.txt`: short summary the orchestrator writes at the end. Not injected later.
- `<id>/verify.log`: verify output. Not in any prompt by design, and not capped if someone reads it.
- `<id>.finish.json`: webhook attempts. No secrets. Not a context file.

### What is not compacted

The finish webhook body stays small: `{ job, status, branch }`, plus `round` and `followUp` after round 1, plus `verifier` / `verification` when a verdict exists (`payloadOf`). It does not include the goal, notes, or logs. Keep it that way.

There is no mid-job summary, no clip when a worker prompts the orchestrator, and no re-injection when the session compacts. `archiveVerifierResult` is the only "archive", and it is a filename rotation.

## Top 3 gaps

1. **No capped snapshot for the orchestrator.** Limen's wake carries a 1200-character excerpt and tells the coordinator the rest is in the job record. Orca tells the orchestrator to read `job.json`, result files, and verifier evidence, and the follow-up steer sends only the raw human sentence. That is the expensive path on long jobs and on Opus. **This is the one to build.**
2. **No per-turn re-injection after compaction.** Limen's hidden cue is rebuilt every call, so the rules survive Pi compaction. Orca cannot do that portably: Claude and Pi both run, and the product must not install a hook in the target repo. A digest injected on steer, plus a prompt line that says to run `orca digest` when a worker note arrives, is the subset that fits. Do not build a Pi extension.
3. **No worker-session continue.** Limen `continue` keeps seam knowledge by copying the jsonl. That increases memory, fights the fresh verifier, and README already skips resume. Repair stays a new worker pane with a short task. Do not build continue.

Not selected, on purpose: tool-call supervisor, groups, keeper, picture, OptChat, closing overview, prune.

## Implementation brief: bounded job digest

One feature: `orca digest`. A pure, capped text snapshot of the job, printed by the CLI and prepended to `orca steer`. It replaces "read the job file and the logs" as the orchestrator's default context. It does not compact the pane, does not copy a session, and does not add a process.

### User-facing behavior

`orca digest <id> [--cwd <repo>]`

- Prints the snapshot to stdout and exits 0.
- Does not write a file, does not change status, does not call herdr, does not send a webhook.
- Unknown id exits 1, same as other commands.
- `orca help` lists it.

The orchestrator and Olaf use it the same way. After a worker note, the orchestrator runs `orca digest <id>` instead of opening `<id>.json` or `verify.log`. It opens `results/<name>.json` only when the digest says that worker's note is missing or `ok` is not true, and it does not paste more than the digest already showed.

`orca steer <id> "message"` still records `job.steers[].message` as the human text only. The prompt sent to the pane is the digest, a blank line, then `Owner steer:` and the message. Do this on every steer, including a mid-job steer, not only follow-ups. A compacted session needs the contract back whenever a human message arrives. The human text stays last so it is the instruction.

First line of the digest must be at least 20 characters and stable, so `promptSeenInPane` (first long line, 40 characters) still recognizes a submitted steer. Use:

`Orca digest for <id> (capped snapshot, not the job file).`

### What the digest contains, and what it drops

Hard cap: 2400 characters. If the assembled text is longer, slice and end with:

`… capped; full records stay in .orca/jobs/<id>/`

Do not read `verify.log`, session transcripts, worker panes, or `job.workers[].task` into the text. Those are the unbounded parts.

Assemble, in order, then apply the hard cap:

- Header line above.
- `status`, `round` (omit round when it is 1), `branch`, `keep` if true.
- Goal: first sentence, or 240 characters, whichever is shorter. If cut, add `…`.
- Worktree path, display-capped at 120 characters.
- Summary: `summary.txt` if it exists, else `job.summary`, first 400 characters. If the file is over 4 KB, read only the first 4 KB. If absent, `summary: none`.
- Workers, at most 8: `name`, `role` if verifier, and the note file's first 160 characters. If `notes/<name>.txt` is missing, `note missing`. If a note file is over 4 KB, do not read past 4 KB. If there are more workers, one line `N more workers in notes/`. Do not print the task string stored on the job.
- Verifier: `verdict`, `rounds`, stall check names if `job.verifier.stall` is set. Up to 3 blocking items from `results/verifier.json`, check name plus evidence sliced to 200 characters. If that file is over 64 KB, do not parse it; print `results/verifier.json is N bytes; not inlined`. Warnings: count only, not bodies.
- Last steer: first 200 characters of the latest `job.steers` message, plus how many earlier steers exist. This is the human text already stored, not a second copy of the digest.
- Fixed contract, under 500 characters: shared worktree, do not implement, do not push, do not create a branch or worktree, do not close panes, `orca done` sends the finish webhook, do not run `orca webhook` or `orca stop`, a follow-up round must call `orca done` again, the verifier stays a fresh worker, do not read the job JSON or `verify.log` into the turn.

### Tests

### Risks on an 8 GB VPS

- Unbounded logs in the prompt: avoided by the 2400-character cap, the 64 KB skip before parse, and by never reading `verify.log` or `workers[].task`.
- A huge `<id>.json` is already parsed by `load` for steer and status. Digest must not make a second full copy of worker tasks in the output.
- No extra daemon, watcher, or supervisor. Digest is one short-lived Node process.
- Steer prompts grow by at most 2400 characters plus the message. That is smaller than the orchestrator prompt already sent at `orca run`, so the existing paste/retry path stays valid if the first line is the stable header.
- Do not append digests to a log file. Compute, print or prompt, discard.
- Do not put the digest in the webhook. A cap bug there would leak job text to the finish endpoint and change a payload tests pin.
