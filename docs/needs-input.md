# Needs-input watcher

A job must never sit silently waiting for an answer. `orka run` starts a detached watcher (`orka watch <id>`, log at `.orka/jobs/<id>/watcher.log`, pid in `job.watcherPid`). When the orchestrator agent is `blocked`, or `idle` for over a minute without the job being finished, it POSTs through the same `finish-webhook.env` config:

```json
{"kind":"needs-input","job":"<id>","title":"<title>","status":"blocked","question":"<text of the question on the pane>","pane":"<orchestrator pane>"}
```

`status` is `blocked` or `idle`. Each waiting episode is posted once. The watcher exits only when the job is `done`, `failed` or `stopped` (`markTerminal` also stops it), the job file is gone, or on its own `SIGTERM`. Closing panes never stops it: it runs in its own session, treats herdr errors, a closed worker pane or an unreachable orchestrator agent as transient (retry with 2s to 60s backoff, logged once as `not answering` / `reachable again`), and a failed read or post only skips that alert. The finish webhook is sent by `markTerminal` right after the status is saved and before any pane cleanup, with no herdr lookup, so it fires whatever the pane state. With no webhook configured it logs and skips. `orka watch <id> --dry-run` prints what it would do. Claude Code's own housekeeping popups ("Teach auto mode about your environment?", session feedback survey) are not questions: the watcher dismisses them itself with `herdr agent send-keys`, logs `housekeeping-dismissed <id> <name>`, and sends no alert. The known popups live in `HOUSEKEEPING_POPUPS` in `lib/watch.mjs` (name, matcher regex, dismiss keys); the matcher only sees the last 15 non-empty pane lines and must target the dialog's own title, so add an entry there only with an exact dialog title. A follow-up `steer` on a finished job starts a new watcher. Workers never post; only `orka done`, `stop` and a failed `run` send the finish wake.
